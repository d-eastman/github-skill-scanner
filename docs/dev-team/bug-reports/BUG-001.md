## Steps to Reproduce

1. Open the app in a screen reader (e.g., VoiceOver on macOS, NVDA on Windows)
2. Observe the loading state while `data/skills.json` is being fetched
3. Note: the list container does not announce a busy state to the screen reader

Alternatively, inspect `src/fe/App.tsx` — the loading state branch renders a `<p>Loading skills...</p>`
inside a `<section aria-label="Skill catalog">` but that `<section>` (or its child container) has no
`aria-busy="true"` attribute while the fetch is in flight.

---

## Expected Result

Per `docs/dev-team/user-flows.md` section 3, State 1 (Loading):

> `aria-busy="true"` on the list container while loading; remove on transition.

The list container element should carry `aria-busy="true"` during the loading state, transitioning
to `aria-busy="false"` (or removing the attribute) when status transitions to `ready` or `error`.
This allows screen readers to announce the container's busy state to users navigating to it.

---

## Actual Result

`aria-busy` is absent from the list container entirely. The `<section aria-label="Skill catalog">`
element has no `aria-busy` attribute in any state. Screen readers will not receive a busy-state
signal during data fetch.

Confirmed by grep on `src/fe/App.tsx`:
```
aria-busy NOT FOUND in App.tsx
```

---

## Evidence

Code inspection of `src/fe/App.tsx`. The loading state branch (lines 103-109) renders:
```jsx
{status === "loading" && (
  <>
    <SearchBar value={query} onChange={setQuery} disabled={true} />
    <p>Loading skills...</p>
  </>
)}
```

No `aria-busy` attribute is set on the `<section>` or any wrapper element during this state.

---

## Frequency

[x] Happens every time — every page load passes through the loading state; aria-busy is never set.

---

## Hypothesis

The implementation correctly renders loading-state UI (disabled SearchBar, loading text) but did not
add the `aria-busy` attribute. The most likely fix is to add `aria-busy={status === 'loading'}` to
the `<section aria-label="Skill catalog">` element in `App.tsx`. This is a one-line change.

---

## Workaround

The loading text "Loading skills..." is present in the DOM and will be read by a screen reader if
the user navigates to it. The app is functionally usable without `aria-busy`; this is a screen
reader UX polish gap, not a functional failure.
