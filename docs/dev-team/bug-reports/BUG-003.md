# Bug Report
**ID:** BUG-003
**Title:** TC-254 passes without asserting the `Accept: application/vnd.github.raw` header — the named invariant is never verified
**Author:** Remy Dubois (QA Engineer)
**Date:** 2026-06-05
**Build / Commit:** HEAD (main) — GHES implementation pass

---

## Severity

[ ] **Critical** — Data loss, security vulnerability, or system unavailable for primary use case
[ ] **High** — Feature is broken for a significant user path; no workaround
[x] **Medium** — Feature works but with significant degradation; workaround exists
[ ] **Low** — Minor issue, cosmetic, or edge case with acceptable workaround

Clarification: the bug is in the test, not the product. The scanner functions correctly via the
base64 JSON fallback path. However, a test named "TC-254: Accept: application/vnd.github.raw
header present in contents fetch request" that never actually checks whether that header is present
gives false confidence that the raw-media-type path is verified. It is not. Additionally, the raw
text path in `fetchRawContent` is currently unreachable in production because `buildHeaders` only
sends `Accept: application/vnd.github+json`, never `application/vnd.github.raw`. This means a
code path documented as "preferred" in ADR-006 Decision 3 is dead code. Both the weak assertion
and the dead code path need to be surfaced clearly to the Lead before the implementation is
considered complete.

## Priority

[x] **Fix in next sprint** — Important but not a release blocker

The scanner works in practice (github.com returns the base64 JSON envelope when
`Accept: application/vnd.github+json` is sent, and the base64 fallback decodes it correctly).
This is not a current outage. It IS a test-quality gap and a documentation inaccuracy that
should be resolved before any real GHES deployment is attempted — GHES behavior on the
`Accept: application/vnd.github.raw` header may differ and is currently untested.

## Steps to Reproduce

1. Read `tests/scanner/ghes.test.ts` TC-254 body:
   ```ts
   it("TC-254: Accept: application/vnd.github.raw header present in contents fetch request", async () => {
     fetchSpy = vi.spyOn(global, "fetch").mockResolvedValue(
       makeResponse("raw content", { contentType: "text/plain" })
     );
     await fetchRawContent(GHES_HOST, "team-a", "skills", "main", "SKILL.md");
     // githubFetch sends headers — check that Accept: application/vnd.github.raw is included
     // Note: githubFetch itself sets Accept: application/vnd.github+json by default.
     // The contents fetch sets a more specific Accept header. Check for the raw media type.
     expect(fetchSpy).toHaveBeenCalledOnce();   // <-- THE ONLY ASSERTION
   });
   ```
2. Observe: the only assertion is `toHaveBeenCalledOnce()`. The comment says "check for the raw
   media type" but no assertion on the Accept header value exists.
3. Run `npm run test` — the test passes.
4. Separately verify `buildHeaders` output:
   ```ts
   const h = buildHeaders("github.com");
   console.log(h["Accept"]);  // → "application/vnd.github+json"
   ```
   Confirmed: `buildHeaders` sends `application/vnd.github+json`, never `application/vnd.github.raw`.

## Expected Result

TC-254 should capture the `init.headers` argument passed to the mocked `fetch` and assert:
```ts
const [_url, init] = fetchSpy.mock.calls[0] as [string, RequestInit];
const acceptHeader = (init.headers as Record<string, string>)["Accept"];
expect(acceptHeader).toBe("application/vnd.github.raw");
```

If the implementation does not currently send `Accept: application/vnd.github.raw`, the test
should fail, prompting the Lead to either:
(a) add the raw Accept header to content fetches in `fetchRawContent` or `githubFetch`, OR
(b) update TC-254 to document that only `application/vnd.github+json` is sent, and remove the
    comment claiming the raw media type is "checked."

The dead-code path (text/plain branch in `fetchRawContent`) should either be reachable or removed.

---

## Actual Result

TC-254 passes with only `expect(fetchSpy).toHaveBeenCalledOnce()`. The Accept header is never
inspected. `buildHeaders` sends `Accept: application/vnd.github+json`, not
`Accept: application/vnd.github.raw`. The "preferred" raw-bytes path described in the
`fetchRawContent` JSDoc and ADR-006 Decision 3 is dead code in the current implementation.

In practice the scanner works because github.com returns a JSON envelope with base64 content
when `Accept: application/vnd.github+json` is sent (TC-251 correctly tests this path), and
`fetchRawContent` decodes it correctly. But:
- The `Accept: application/vnd.github.raw` path is untested and unreachable.
- TC-254's name and comment make a false claim about what is verified.
- A GHES instance may behave differently from github.com when it receives only the JSON Accept
  header; this is uncharted.

   Accept header, github.com always returns JSON.
4. Confirmed via a vitest run:
   - `buildHeaders("github.com")["Accept"]` === `"application/vnd.github+json"` (PASS)
   - `buildHeaders("github.com")["Accept"]` does NOT contain `.raw` (PASS)

## Hypothesis

The test was written with the intention of verifying the raw Accept header, as indicated by the
comment. The implementation in `buildHeaders` was not updated to send `application/vnd.github.raw`
specifically for content fetches (as ADR-006 Decision 3 describes as "preferred"), and the
`githubFetch` signature does not accept header overrides. The test was then left with only the
`toHaveBeenCalledOnce()` assertion, which always passes regardless of headers sent.

The Lead either intended:
- `fetchRawContent` to call `fetch` directly with a custom Accept header (not via `githubFetch`),
  which would bypass PAT routing — a different problem; or
- `githubFetch` to accept an optional headers argument so callers can specify a different Accept,
  which was not implemented; or
- The raw Accept header to be sent unconditionally by `buildHeaders` for all calls (imprecise but
  works for content calls).

The ADR-006 Decision 3 notes say "send `Accept: application/vnd.github.raw`" but this is the
responsibility gap: `buildHeaders` serves all call types (repo info, trees, contents) and sending
`.raw` on non-content calls may be wrong. The cleanest fix is to either allow `fetchRawContent` to
override the Accept header or to add a `buildContentHeaders` variant that sets `.raw`.

---

## Workaround

The scanner works in practice. The base64 fallback path is correctly implemented and tested (TC-251).
For github.com production use, no workaround is needed — the scanner produces correct output.

For GHES deployment: manually verify that the target GHES instance returns a parseable JSON envelope
(base64 encoding) when `Accept: application/vnd.github+json` is sent to its Contents API. If it does
not, the scanner will fail to extract content silently. This is the operational risk until TC-254 is
properly fixed.
